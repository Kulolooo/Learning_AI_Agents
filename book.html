00 · 导论：为什么值得从零写一遍

智能体是一种工程结构：把模型放进循环，再给循环装上边界。模型本身没有变，变的是它被放在什么位置。理解了这层结构，框架选型、成本控制和可靠性治理会变成同一道题的三种问法。

这个库解决什么问题

围绕智能体的材料大致分三类。论文给出概念，很少给工程细节；框架文档给出接口，很少解释为什么这样设计；教程给出可运行的 notebook，但代码量与概念量往往同时膨胀。三者之间有一条缝：使用者能跑通示例，却说不清自己在做什么取舍。

01 · 智能体的定义与最小闭环

判断一个系统是不是智能体，看两件事：控制流由谁决定，能不能读到自己上一步的结果。模型多大不参与这个判断。

学习目标

读完本章，应当能够用四个要素判断一个系统属于哪一档自主度，写出一个不依赖框架、可以被单元测试覆盖的循环，说明循环成本为什么随步数呈平方增长，并为循环接上可回放的轨迹。

1.1 三个必要条件

工程上判断一个系统是否为智能体，通常看三条是否同时成立：目标以自然语言给出，而不是以固定参数给出；行动通过工具作用于外部世界，例如检索、读写文件、调用接口；下一步依赖上一步的观察，也就是存在反馈回路。只满足前两条的系统更接近带工具的单次调用，只满足第一条和第三条的系统通常叫多轮对话，三条齐备才构成循环。这个区分有实际用途，因为三条各自对应一类失败模式，缺哪一条就少一类防护。

由此可以排出四档自主度，成本与风险自上而下递增。固定工作流的控制流由人写死，适合步骤稳定、可以枚举的场景；路由由代码或分类器决定分支，适合意图可分类、分支有限的任务；单智能体的循环由模型决定下一步，适合工具充分、路径不确定的任务；多智能体再由模型在角色之间协调，适合角色确实异质、任务足够长的情况。选择顺序应当是前两档优先，因为它们的失败可以复现、可以断言，而自主循环的失败往往只能靠轨迹事后归因。

档位控制流由谁决定典型形态适用条件
L0人写死固定工作流（DAG）步骤稳定、可枚举
L1代码加分类器路由到不同模板意图可分类，分支有限
L2模型加循环ReAct 单智能体工具充分、路径不确定
L3模型加多角色主管、辩论、黑板角色确实异质、任务足够长

1.2 循环的四个组件

图 1-1　控制循环（上）与它依赖的状态层、控制层（下）。循环本身只有十几行，复杂度全部来自两侧的支撑。

模型负责在候选动作中做选择，工具负责把选择变成对世界的作用，状态负责记住做过什么、看到了什么，边界负责决定何时停下。任一处缺失，症状都很明确：没有工具，模型只能描述而不能执行；没有状态，每一轮都从零开始，重复劳动；没有边界，循环可能在两句客套话之间来回。

一个可以直接运行的骨架如下，完整实现见 learning_agents/agent.py。

messages = [system_prompt, user_task]
for step in range(max_steps):
    if budget.exceeded(usage):
        return stop("budget")
    resp = llm.complete(messages, tools=registry.schemas())
    if not resp.tool_calls:
        return answer(resp.text)          # 模型主动收尾
    messages.append(assistant_message(resp))
    for call in resp.tool_calls:
        result = registry.execute(call)   # 永不抛异常：错误也是结果
        messages.append(result.to_message())
return stop("max_steps")

这段代码有三个细节决定了它能否上生产。registry.execute 不抛异常，而是返回结构化结果，错误作为观察回灌，模型才有机会换参数、换工具或者承认失败。每一轮把 tool_calls 与 tool 消息成对写回，顺序与 id 必须匹配，否则模型会把两条观察对错号。预算在调用模型之前检查，而不是之后，先花钱再判断等于没有预算。

1.3 成本为什么是平方级

设第 $i$ 步的上下文为 $S_i$，每步新增的观察与决策为 $\Delta$，则第 $i$ 步的上下文约为 $S_0 + i\Delta$，$n$ 步的总消耗为

$$ T(n)=\sum_{i=1}^{n} S_i \approx nS_0 + \frac{n(n-1)}{2}\Delta . $$

步数翻倍，总 token 大约翻四倍。两个经验值由此而来。单智能体的步数上限通常设在 4 到 10 步之间，超过 10 步的任务更适合拆成子任务或者改成显式计划；把每步的新增内容 $\Delta$ 压掉一半，总成本降幅接近一半，而且越到后面的步数省得越多。这也解释了为什么上下文压缩在长任务里的收益被放大。

1.4 终止条件

条件触发防的是什么建议值
final模型不再请求工具正常收尾—
max_steps达到步数上限思考过久、路径发散4 至 10
budget_tokens累计 token 超限成本失控单任务 2 万至 10 万
loop_detected同工具同参数连续 N 次原地打转N 取 2 至 3

四类条件覆盖的失效模式互不重叠。前两类防想太久，后两类防绕圈子。只设 max_steps 的系统在长上下文里依然可能烧掉十倍预算，只设预算的系统则可能第三步就把额度花光，交回一个半成品答复。工程上还应记录停下的原因，stopped_reason 是评估和告警的第一字段。某一周内 max_steps 的比例突然升高，通常意味着工具描述或者提示词发生了回归。

1.5 轨迹

learning_agents/trace.py 把每个动作落成事件，按行追加写入 JSONL。一次两步的运行为：

agent.start   {"task": "请帮我计算 (128*7+36)/4 的结果", "tools": 1}
agent.step    {"step": 1, "tokens": 199}
llm.response  {"step": 1, "tool_calls": ["calculator"], "tokens": 211}
┌─ tools {"names": ["calculator"]}
  │  tool.call: calculator {"ok": true, "duration_ms": 0.06}
└─ end tools (0.0ms)
agent.step    {"step": 2, "tokens": 245}
llm.response  {"step": 2, "tool_calls": [], "tokens": 313}
agent.end     {"stopped": "final", "steps": 2, "tokens": 524}

事件类型只有六种，却足以回答排障中最常见的四个问题：调用了哪个工具，参数是什么，花了多少 token，在哪一步停下。第 10 章会把这份轨迹变成可以断言的评估输入。

1.6 接入真实模型

离线示例使用 RuleBasedLLM，作用是让控制流可见，不代表真实模型的能力边界。切换到兼容 OpenAI 协议的服务只需改一行。

from learning_agents.llm import OpenAICompatLLM
from learning_agents.agent import Agent

agent = Agent(llm=OpenAICompatLLM(model="gpt-4o-mini"), tools=registry)
result = agent.run("把这周的销售数据汇总成三条结论")

需要的环境变量是 OPENAI_API_KEY、OPENAI_BASE_URL 与 OPENAI_MODEL，其中后两个可以省略。客户端只依赖标准库，超时与重试次数显式可配；429 与 5xx 才重试，其余 4xx 直接失败。把不可重试的错误重试三次，只会把延迟放大三倍，并不会提高成功率。

工程要点

先把终止条件写出来，再写循环体。顺序反过来的项目，通常能跑但不能停，只能靠外层超时兜底。

状态要可序列化。循环里不要长期持有数据库连接、文件句柄、线程锁，第 09 章的检查点依赖这一点。业务规则中的硬约束，例如权限、金额上限、输出格式，应当放在代码里校验，只有风格和取舍留给提示词。

一次只加一个自由度。先加工具，再加记忆，再考虑多智能体，每加一层重跑一遍评估集。同时增加两个能力而未分别度量，一旦指标下降就无法判断是哪一层造成的。

02 · 上下文工程：把提示词当程序写

模型的"记忆"只有上下文窗口。上下文工程是在有限窗口里做预算分配与信息压缩，让每一步决策拿到恰好够用的信息。

学习目标

读完本章，应当能够拆解一次请求的上下文构成并给出预算表，在四种压缩策略之间按信息损失与成本排序，理解位置效应与缓存命中对提示结构的要求，并用结构化输出把自然语言约定换成可校验的契约。

2.1 上下文是唯一的编程接口

传统程序通过函数签名传参，智能体通过上下文传参。角色、权限、格式、可用工具、历史事实都要挤进同一段文本，争夺同一个预算。由此得出一个不太直观的结论：提示词写得好不好，主要不取决于措辞，而取决于信息的选择与排序。同一批信息，把当前任务放在三千字历史之后，模型对它的关注度会明显下降，这类现象通常称为 lost in the middle。

图 2-1　把窗口当预算表：先分配，再压缩。右侧三类内容不可压缩，必须预留。

2.2 预算表

设窗口为 $B$，一次请求由六部分组成：系统提示 $S$、工具 schema $T$、长期记忆或检索结果 $M$、历史对话 $H$、当前任务 $Q$、输出预留 $O$，满足 $B \ge S+T+M+H+Q+O$。

部分含义常见占比可否压缩
$S$角色、规则、风格10% 至 15%可精简，不可删约束
$T$工具 schema8% 至 15%可精简描述
$M$长期记忆、检索结果10% 至 25%可换更少更准的片段
$H$历史对话20% 至 40%可摘要、可截断
$Q$当前任务5% 至 10%不可压缩
$O$输出预留15% 至 25%不可压缩

输出预留最容易被忽略。模型生成的答复同样占用窗口，思维链越长占用越多。把输出上限写进预算，比事后截断安全，因为截断会把一句结论切成半句，而模型并不知道自己被切了。一个可用的起点是历史不超过 30%，检索不超过 25%，输出预留 20%；历史突破 30% 之后，回答质量的下降通常已经可以测出来。

2.3 四种压缩策略

策略做法信息损失额外成本适用
截断丢弃最早的对话高，会丢约束和数字无短会话、闲聊
工具输出摘要大结果先摘要再回灌中一次小模型调用日志、长文档
滚动摘要把旧对话压成事实清单中高周期性调用长会话、客服
检索替代历史入索引，按需召回低，但可能召回失败建索引与检索跨天、跨会话

选择原则是按代价从低到高试，而不是按效果从好到坏选。截断零成本，先看够不够用；确认丢了关键信息，再升级到摘要。反过来，一上来就做全量检索，会把一个两百毫秒的请求拖到两秒，还引入召回失败这个新的故障点。

有一条经验容易被忽略：数字与人名不要进摘要。摘要模型倾向于把"3.2%""订单号 20241105"这类细节抹平，而后续步骤要用它们。稳妥做法是把结构化事实单独存一份键值，摘要只压叙述性内容。

2.4 消息结构与位置效应

一条稳定的消息序列通常是这样排列的：系统消息给出角色与硬规则；另一条系统消息放参考事实，并带来源编号；用户消息给出当前任务、示例与验收标准；中间是循环产生的历史；末尾是本轮追问。

[system] 角色 + 硬规则 + 输出格式
[system] 参考事实（检索/记忆，带来源编号）
[user]   当前任务（含示例与验收标准）
[assistant/tool] ... 循环产生的历史 ...
[user]   本轮追问（如有）

这套顺序对应三条经验。硬规则前置且少改，前缀稳定才能吃到前缀缓存的折扣，每改一次系统提示，缓存全量失效。参考资料与任务分开，混在一条消息里，模型容易把资料里的说法当成用户的要求。示例紧跟任务，放在最前面会被后续内容稀释。

2.5 结构化输出

自然语言约定在压力下会失效：模型可能加解释、加 markdown 代码块、少字段。可行做法是三层防御。

raw = llm.complete(prompt, response_format={"type": "json_object"}).text
data = validate_json(raw, {
    "required": ["intent", "confidence"],
    "properties": {
        "intent": {"type": "string", "enum": ["refund", "invoice", "other"]},
        "confidence": {"type": "number"},
    },
})

请求侧声明格式，解析侧容忍代码围栏与尾逗号，schema 层做最终校验。第三层最重要，因为它把"模型是否听话"变成了"系统是否接受"。失败时把错误信息回灌让模型重试一次，仍然失败就走降级分支。没有校验的结构化输出，只是看起来像结构化的文本。

2.6 装配的实现

learning_agents/memory.py 里的 MemoryManager.build_context 把三层记忆拼成一段带标签的文本。

manager.observe("user", "我们上季度的退货率是多少？")
manager.remember("门店 A 的退货率连续两季高于均值", importance=0.8)
context = manager.build_context("退货率 门店 A 的对比", k=2)

输出形如：

[长期事实]
- (2026-08-22) 门店 A 的退货率连续两季高于均值

[相似任务]
- 统计上季度退货率 => 退货率 3.2%，低于阈值 5%

[近期对话]
user: 我们上季度的退货率是多少？
assistant: 3.2%，来源：订单表按月聚合。

标签不是装饰。它让模型知道每段信息的可信度与时效，从而在冲突时优先采用近期对话，而不是半年前的事实。日期同理，写进括号里比让模型自己推断"这条是不是过时"要可靠。

工程要点

预算先于内容。先算 $S+T+M+H+Q+O$，再决定放什么；反过来一定超。每次压缩都要记录压缩前 token、压缩后 token 与被丢弃的内容，否则质量下降无法归因。提示词要进版本库，有 diff、有评审、有回归测试。

用户输入不要拼进系统提示。这是提示注入的入口。用户内容一律放在 user 消息里，并明确标注来源，让模型知道哪些是资料、哪些是指令。

常见失败模式

约束失效时不断追加措辞，是提示膨胀的起点。正确的做法是把约束移进代码校验，提示里只保留无法用代码判断的部分。

滚动摘要之后模型开始编造金额与日期，多半是摘要吃掉了数字。检索结果塞进八个片段而真正相关的只有一个，模型会被噪音带偏，宁少勿多，top-3 通常优于 top-8。

系统提示里塞时间戳或随机 ID，会让每次请求的前缀都不同，缓存全部失效。这类问题不体现在正确率上，只体现在账单上。

练习

  2. 写一个 ContextBudget 类：给定各段文本与预算，按优先级截断，并返回被丢弃的段落清单。
  3. 给 validate_json 增加数组元素类型校验，并为"多返回一个字段"设计策略，说明选择拒绝还是忽略的理由。

03 · 工具调用：模型唯一的"手"

模型看不到你的代码，只能看到工具的名字、描述与参数 schema。这三样东西合起来就是全部的用户界面，写得含糊，等于让模型蒙着眼睛操作。

学习目标

读完本章，应当能够用四条原则设计工具 schema，并说清每条原则对应的失败模式；能讲出一次工具调用在运行时的完整时序，以及每一步的错误处理；能为副作用工具设计幂等键与审批门；能区分可重试错误与应上报错误，并让模型在文本里看见这个区别。

3.1 工具是接口，不是函数包装

把业务函数直接暴露给模型，是常见的第一个错误。函数签名面向程序员，可以传对象，可以抛异常；工具 schema 面向概率模型，只能填 JSON，只能读文本返回。两套契约的差异需要显式处理，否则代码侧的类型约束到了模型侧完全不存在。

面向函数工具
参数任意类型、可选依赖注入扁平 JSON，字段越少越好
返回对象 / 异常文本（或可序列化的结构）
失败抛异常由上层捕获返回结构化错误，交给模型决策
语义调用方知道上下文模型只读描述，必须自解释

3.2 schema 设计的四条原则

第一条是动词开头、语义单一。get_order_status 优于 order，search_docs 优于 docs。一个工具只做一件事，模型才可能选对；manage_order 这类"万能工具"会让模型在参数里做二次决策，错误率显著上升。第二条是描述要写"何时用"，不能只写"做什么"。

@tool
def lookup_faq(topic: str) -> str:
    """查询内部知识库中的常见问题，topic: 主题关键词

    仅在用户询问政策、流程、时效时使用；不要用于查询具体订单状态。
    """

上面这段描述里，第二段话比第一段更重要，因为它排除了一种误用。工具描述里写清"不用于什么"，往往比写"用于什么"更能降低误调用率。第三条是参数少而必要，超过五个参数通常意味着该拆，可选参数要么给默认值并写进 schema，要么删掉，模型对"可选"的理解极不稳定。第四条是返回可控，固定上限默认 4000 字符，超出即截断并显式标注 …[输出已截断]。一个返回两万行日志的工具会瞬间吃掉上下文预算，还会稀释真正重要的信息。

工具声明中的 side_effect 与 idempotent 属于控制点，不能当注释看：

@tool(side_effect=True, idempotent=False)
def send_notice(channel: str, message: str) -> str:
    """向指定渠道发送通知（有副作用，需要人工审批）"""

审批门、审计日志、灰度开关都挂在这两个字段上。

3.3 一次调用的完整时序

图 3-1　模型的输出只是一份意图，执行发生在运行时。④ 与 ⑤ 是两道最容易漏掉的闸门。

参数校验必须放在执行之前，缺参、类型不符、出现未声明字段都应返回结构化错误，静默忽略会让模型以为调用成功，进而在错误前提上继续推理。结果与错误则走同一条通道回灌，都用 role="tool" 的消息，模型才能在同一种语义下比较成功与失败。这两点对应图上的 ④ 与 ⑤，跳过任何一道，错误都会以"成功"的形态进入下一轮。

3.4 错误分类：让模型知道该不该重试

把错误分成四类，并让文本本身携带可行动信息：

类别例子模型应做的动作文本前缀建议
参数错误缺必填、类型不符修正参数后重试一次INVALID_ARGUMENT:
瞬时故障超时、429、连接重置退避后重试，或换工具RETRYABLE:
永久故障404、权限不足换路径或上报PERMANENT:
业务拒绝审批未通过、额度不足停止并解释DENIED:

不加前缀时，模型面对一段 Traceback 往往选择再试一次同样的调用，因为它无法区分参数写错与服务抖动。加了前缀，重试行为会立刻变得合理：RETRYABLE: 的先退避再重试，或者换工具；PERMANENT: 的换路径或上报；DENIED: 的停止并解释。

3.5 幂等与审批

副作用工具需要三件东西：幂等键、审批门与审计日志。幂等键取 idempotency_key(tool, arguments) 的哈希，同一请求重复到达时直接返回首次结果，避免再发一次货。审批门 ApprovalGate 默认拒绝，默认值取"不做"，因为安全的默认值只能落在"不执行"这一侧。审计日志记下谁在什么时候批准了什么参数，它既是合规证据，也是复盘材料。

registry.hook = ApprovalGate(approver=lambda req: "退款" in str(req.arguments)).hook

被拒绝时，工具返回 ERROR: ApprovalDenied，循环继续，模型据此改写策略或直接说明需要人工处理。审批失败不中断整个任务，它只是又一个观察。

3.6 并行调用与顺序回填

模型一次可能返回多个 tool_calls。并行执行能把三段串行 300ms 压成 300ms，但有两条约束：副作用工具不得并行，否则幂等键与审批顺序都会失效；结果必须按请求顺序回填，tool_call_id 一一对应，顺序错位会让模型把 A 的结果当成 B 的。

learning_agents/tools.py 的 parallel_execute 用线程池实现，并保持输入顺序：

calls = [ToolCall("1", "add", {"a": 1, "b": 2}), ToolCall("2", "boom", {"text": "x"})]
results = parallel_execute(registry, calls)   # 顺序与 calls 一致

3.7 协议：MCP 解决了什么

模型上下文协议（Model Context Protocol）把"工具如何被描述与调用"标准化为客户端—服务器结构：主机（Host，如 IDE 或桌面应用）持有模型与用户授权，客户端连接一个或多个服务器，服务器暴露 tools / resources / prompts。它解决的是复用与授权这类问题：同一个数据库工具，不必为每个框架重写一遍适配层；权限与授权在主机侧统一管理，不必散落在每个工具实现里；工具的 schema 与实现可以独立演进、独立部署。

对本库的实现而言，MCP 的价值是把第 3.2 节的四条原则固化成协议字段：name、description、inputSchema 强制存在，服务器能力在握手时声明。自己实现一个最小 MCP 服务器只需百来行，但工具不到三个时不要引入它，协议层的抽象成本只有在工具数量增长之后才会被摊薄。

工程要点

工具名与描述是产品文案，值得像 API 文档一样评审。所有工具都应有超时，没有超时的工具会拖垮整个循环。返回结果优先用结构化数据，{"status": "shipped", "eta": "2024-11-08"} 比"您的包裹已发出，预计 11 月 8 日到达"更容易被后续步骤使用。

工具数量控制在 10—20 个。超过这个量级，模型的选择准确率会下降，应当考虑按领域分组路由（第 05 章），让一次决策只看一组工具。

常见失败模式

描述与实现不一致是最难查的一类问题：文档说返回最近 7 天，代码返回 30 天，模型会基于描述做推理，错误被放大到下游。静默修正参数同样危险，工具内部把 "3" 转成 3 却不告诉模型，下次模型仍然传字符串，问题被掩盖。错误信息泄露内部细节，把完整 SQL、堆栈、内网地址回灌给模型，既污染上下文，也可能被写进最终答复。工具太多则从另一头出问题：20 个工具、每个描述三行，光是 schema 就占掉 15% 预算，选择准确率同时下降。

练习

  1. 给 calculator 增加除零错误处理，返回 INVALID_ARGUMENT: 前缀，并在脚本模型里演示"模型看到错误后改参数"。
  2. 实现一个 with_retry(tool, max_attempts=2) 包装器：仅对 RETRYABLE: 前缀重试，其余直接返回。
  3. 统计 registry.schemas() 的字符数，把它压到 1200 字符以内，观察工具选择是否仍然正确。

04 · 记忆系统：写入比读取更难

存储不是难点。难点是决定"什么值得记、什么时候忘、两条冲突的记忆听谁的"。

学习目标

读完本章，应当能够区分工作记忆、情景记忆与语义记忆各自的职责与淘汰策略，用重要度阈值控制写入成本并说清阈值化带来的漏记风险，设计"相似度 × 新近度 × 重要度"的召回打分，并处理记忆冲突与过期，避免模型自信地给出过时答案。

4.1 三种"记住"

需求时间跨度典型问题对应层
记住刚才说了什么一次会话指代消解、上下文连续工作记忆
记住上次这类任务怎么做跨会话复用成功路径、避开失败路径情景记忆
记住用户是谁、偏好什么长期个性化、少问重复问题语义记忆

把三者混成一份"聊天历史"，是记忆系统最常见的失败：历史越滚越长，关键事实被埋在中间，而成本随长度线性上升。三种记忆的淘汰依据本来就不同，工作记忆按轮数滑窗，情景记忆看时间与成功率，语义记忆看重要度与新近度，混成一份之后，三套依据都无法执行。

4.2 三层架构

图 4-1　写入向下沉淀（压缩、合并），读取向上装配（召回、注入）。两层之间的箭头由策略触发，不会自动发生。

层存什么写入触发淘汰读取
工作记忆最近 N 轮对话每轮滑动窗口每轮全量注入
情景记忆任务→步骤→结果任务结束且成功/失败明确时间 + 成功率任务相似度 top-k
语义记忆事实、偏好、领域知识重要度 ≥ 阈值重要度 × 新近度向量召回 + 重排

4.3 写入：为什么贵

一次写入通常包含四个动作：抽取（把对话变成事实）、去重（和已有记忆比相似度）、冲突检测（新事实是否与旧事实矛盾）、落库。每一步都可能调用模型或做向量计算。

用重要度阈值可以把成本压到可控：

manager.remember("门店 A 的退货率连续两季高于均值", importance=0.8)  # 写入
manager.remember("今天天气不错", importance=0.1)                       # 丢弃

阈值的代价是漏记：一句轻描淡写的"以后都发邮件给我"可能只有 0.4 的重要度，却是一个强偏好。缓解办法是保留两条通道。规则通道在出现"以后""总是""不要"等词，或出现明确的人名、数字、日期时直接提权；手工通道允许用户显式说"记住这一点"，绕过硬阈值。

去重同样重要。同一事实被记十遍，会挤占召回名额并放大它的权重。工程上用近似去重即可，字符 n-gram 的 Jaccard，或向量余弦大于 0.9，都不必上复杂的实体消解。

4.4 读取：三因子打分

单一相似度排序会产生"永远召回同一条"的问题。实践中更稳的打分是三项加权：

$$ \text{score}(m)=\alpha\cdot \text{sim}(q,m)+\beta\cdot e^{-\lambda \Delta t}+\gamma\cdot \text{importance}(m) $$

  • $\text{sim}$：向量余弦或 BM25 归一化分数；
  • $e^{-\lambda \Delta t}$：新近度，$\lambda$ 取 0.01/天量级时，半衰期约 70 天；
  • $\text{importance}$：写入时的重要度，用于保证"关键事实不因时间久而被挤掉"。

起点可以取 $\alpha=0.6,\ \beta=0.25,\ \gamma=0.15$。三个权重应当按业务调：客服场景更看新近度，合规场景更看重要度。

召回数量 $k$ 也要克制。$k=3$ 通常优于 $k=8$：更多片段带来更多噪音，而模型的注意力并不会因此更均匀。

4.5 冲突与遗忘

两条记忆矛盾时（"偏好邮件" vs "偏好电话"），不能让它们同时生效。低成本的解法是把时间戳一起交给模型：

[长期事实]
- (2024-09-12, 置信度 0.9) 用户偏好邮件通知
- (2024-11-03, 置信度 0.9) 用户偏好电话通知，邮件经常漏看

模型看到日期后，通常会自动采用较新的一条。若要更严格，就在读取侧做"同槽位只保留最新"的合并。

遗忘不是可选项。过期事实比没有事实更危险：它会让模型自信地给出错误答案。维护手段有三类：价格、库存、政策类事实带 TTL，过期即不召回；用户说"不对"时，把旧记忆标记为 superseded，不直接删除，以便保留审计链；每类记忆设条数上限，超出时按打分淘汰，避免无限膨胀。

4.6 实现与演示

learning_agents/memory.py 提供四个可直接用的组件：

from learning_agents.memory import BufferMemory, EpisodicStore, MemoryManager, VectorMemory

store = EpisodicStore("memory/episodes.jsonl")
store.append("统计上季度退货率", "退货率 3.2%，低于阈值 5%", ["sql"], True)

manager = MemoryManager(buffer=BufferMemory(max_turns=2),
                        semantic=VectorMemory(), episodic=store, token_budget=600)
manager.observe("user", "我们上季度的退货率是多少？")
manager.remember("门店 A 的退货率连续两季高于均值", importance=0.8)
print(manager.build_context("退货率 门店 A 的对比", k=2))

HashingEmbedder 用特征哈希把 token 映射到 256 维单位向量。它不是语义模型，但保留了词面相似性，足以演示"写入—召回—装配"的完整链路；换成真实 embedding 只需替换 embed 方法。

情景记忆用任务相似度召回，适合"这类报表上次是怎么做的"：

store.similar_tasks("再统计一次退货率")
# [{'task': '统计上季度退货率', 'answer': '退货率 3.2%，低于阈值 5%', ...}]

4.7 怎么评估记忆

指标定义采集方式
命中率需要记忆时，正确事实出现在上下文中的比例构造"必须依赖记忆"的用例
污染率不相关或过期记忆被注入的比例人工抽检 + 规则检测
写入成本每千轮对话的抽取调用次数与 token轨迹统计
冲突率同一槽位出现多版本的比例定期扫描

前三项决定"值不值得做"，第四项决定"要不要停下来清理"。

工程要点

记忆是有状态服务，必须能导出、能回滚、能按用户删除。写入路径要幂等，同一条事实重复写入不应产生多份记录。

不要把整段对话存进语义记忆，先抽取成事实再存。读取时给每条记忆带上来源与时间，模型才有可能正确处理冲突。

常见失败模式

不设阈值、什么都记住，三个月后召回全是噪音，成本翻倍。摘要吃掉数字也同样常见：把"3.2%"压成"较低"，后续步骤就无法引用。忘记遗忘的代价是把去年的价格当成现价，而且模型给出答案时相当自信。跨用户串味则属于安全事故：记忆没有按租户隔离，A 的偏好出现在 B 的上下文里。

练习

  1. 给 MemoryManager 增加 forget(key, reason)，把记忆标记为失效而非删除，并补测试。
  2. 用 score = α·sim + β·recency + γ·importance 重写 VectorMemory.search，观察召回排序变化。
  3. 构造一组"记忆冲突"用例：同一偏好两个版本，验证时间戳注入后模型选择较新的一条。

05 · 规划与路由：先想清楚，还是边做边想

规划的价值不止于让模型"多想一会儿"。它要把隐式推理变成可检查、可修改、可重放的中间产物，有了产物，规划才谈得上被评审、被回退。

学习目标

读完本章，应当能够用一张判定图在固定工作流、路由、计划执行与自主循环之间做出选择，写出可验证的计划并交代粒度、依赖与降级路径，实现带次数上限的重规划并说明上限为什么必须存在，用任务图表达并行分支，解释拓扑分层解决了什么问题。

5.1 先选结构，再谈实现

多数"智能体效果不好"的问题，根源是控制结构选错了：用一个自由循环去处理本就固定的流程，或者用固定流程去套一个边界模糊的任务。

Mermaid 流程图源码（GitHub / Typora / VS Code 可直接渲染）
flowchart TD
    A["任务到达"] --> B{"步骤可枚举?"}
    B -- "是" --> C["固定工作流<br/>成本最低、可审计"]
    B -- "否" --> D{"意图可分类?"}
    D -- "是" --> E["路由 + 模板<br/>分类器 + 分支"]

这张图的价值在于它把"要不要上智能体"变成一个可以回答的问题，而不是一种信仰。越往下的分支，成本与方差越大。

5.2 路由：一步决策的性价比

路由是最被低估的结构。它只做一次分类，却能把 80% 的请求导向确定性路径，只让 20% 的长尾进入自主循环。

router = Router({"billing": ["退款", "发票"], "tech": ["报错", "超时"]})
router.decide("接口超时了")     # 'tech'
router.decide("随便聊聊")       # 'general'（兜底）

路由有三条工程要求。兜底分支必须存在，并且能升级到人工或自主循环；分类结果要落盘，否则无法统计"路由错了多少"；分类器与处理器解耦，换模型、换规则都不影响下游。

路由的失败模式是"边界请求"：一句"我要退款，但系统一直报错"同时命中两个类别。稳妥做法是允许多标签，按优先级取第一个可处理的，并把未处理的标签写进工单。

5.3 计划-执行-重规划

图 5-1　计划是可编辑的状态机；失败时回到待执行队列，而不是从头再来。

最小实现只需要三个角色：

plan = Planner().from_template(
    ["确认数据口径", "拉取明细数据", "生成汇总报告"],
    tools=["spec_lookup", "sql_query", ""],
)
runner = PlanAndExecute(executor=run_step, replanner=replan, max_replans=1)
runner.run(plan)

executor 负责执行单步，replanner 负责在失败后改写剩余步骤。两者分离的好处是：执行逻辑可以单测，重规划策略可以单独评估。

重规划必须设上限。重规划本身会消耗模型调用；若失败原因是系统性的，例如表不存在、权限不足，重规划只会不断生成"看起来可行"的新计划，把一次 3 秒的失败拖成 30 秒的超时。上限通常取 1—2 次，超过即上报。

5.4 什么是一个好计划

用四条标准检查模型产出的计划：

标准检查问题不合格的例子
可验证每步有明确的完成判据吗"分析数据"
粒度合适一步是否约等于一次工具调用"查数据并写报告并核对"
依赖显式哪些步骤可以并行未标注依赖，串行执行
可降级失败时有没有替代路径只有一条路径

"分析数据"之所以不合格，是因为无法判断是否完成；改成"按门店汇总近 90 天退货率，输出 CSV"，就同时获得了可验证性与粒度。

计划步骤还应当携带预期产物。有了产物声明，执行器就能校验"这一步真的产出了东西"，不再只看工具是否返回 200。

5.5 任务图：把并行写进结构

当步骤之间存在依赖时，用图表达依赖关系，列表无法承载这种结构。TaskGraph 用拓扑排序分层，同一层可以并行：

graph = TaskGraph()
graph.add("抓取", fetch)
graph.add("抽取1", extract_a, deps=["抓取"])
graph.add("抽取2", extract_b, deps=["抓取"])
graph.add("汇总", merge, deps=["抽取1", "抽取2"])

graph.layers()   # [['抓取'], ['抽取1', '抽取2'], ['汇总']]
graph.run(parallel=True)

分层的意义在于把"能并行"变成结构事实，调度不再依赖执行器的直觉。它同时天然检测循环依赖：若某一层为空而仍有剩余节点，说明图里有环。

5.6 动态重规划 vs 一次性计划

维度一次性计划动态重规划
成本一次规划调用每次失败一次额外调用
适应性差（环境变化即失效）好
可预测性高（可提前估算步数）低
适用步骤稳定、工具可靠工具不稳定、环境开放

折中方案是分段计划：一次只规划随后的 3 步，执行完再规划下一段。它保留了适应性，又把单次规划的上下文控制在可控范围。

工程要点

计划的每一步都要能映射到一次工具调用或一次子智能体调用；映射不了，说明粒度错了。计划要落盘（Plan.to_dict()），失败时才能对比"计划中的依赖"与"实际的失败点"。

重规划要带失败原因，否则模型会生成与上次几乎相同的计划。路由与计划都需要评估集：前者看分类准确率，后者看计划可执行率，也就是步骤一次通过的比例。

常见失败模式

计划幻觉是规划器最容易犯的错：模型规划了"调用内部风控接口"，系统里却没有这个工具，规划器的提示里必须带真实工具清单。过度规划则从另一头浪费预算，三步能完成的任务拆成十二步，每步都要一次模型调用，成本翻四倍而质量不变。无降级的串行会让第二步的失败作废后面全部工作，高风险步骤应当在计划阶段就准备替代路径。把重规划当重试使同样有害：参数错误也触发重规划，结果生成一堆换汤不换药的计划。

练习

  1. 用 Router 实现一个三分类工单路由，构造 20 条测试语句，统计准确率与兜底比例。
  2. 给 PlanAndExecute 增加"步骤超时"参数，并让超时与业务失败走不同的重规划策略。
  3. 用 TaskGraph 表达"三个数据源并行抓取 → 合并 → 生成报告"，比较串行与并行的总耗时。

06 · 反思与自我修正：用评审换质量

反思只有在"评审标准是外部的、可重复的"时才有效。否则它只是让模型换一种说法再说一遍。

学习目标

读完本章，应当能够区分自评、外部规则与执行结果三种反馈源，为反思循环设计三条终止条件以避免无限改稿与过拟合，实现"捕获错误、生成补丁、重新执行"的自愈代码，并判断哪些任务的反思注定无效，把算力挪到别处。

6.1 三种反馈源

反馈源例子可靠性成本
自评让模型给自己的答案打 1—10 分低（分数漂移、偏乐观）一次调用
外部规则单元测试、schema 校验、引用检查高近乎零
执行结果代码报错、接口 4xx、检索为空高已支付

三种反馈源的可靠性差异很大，能拿到执行结果就不要用自评。自评的价值只在"没有可执行判据"的开放任务上，例如写作、方案设计，而且必须配一个固定的 rubric，否则同一份稿子两次评分能差 2 分。

图 6-1　生成—评审—修订的闭环。三条终止条件里，只有"分数达标"是正向信号，其余两条都是止损。

6.2 三条终止条件

loop = ReflectionLoop(generate, revise, critic, max_rounds=3, min_gain=0.02)
out = loop.run("如何避免智能体在失败路径上失控？")

循环在三种情况下停下。rubric 全项通过算达标，加权平均过线不算数，因为平均分会掩盖某一项的严重缺陷，比如缺少引用。轮数触顶也停，默认 3 轮，经验上第 4 轮之后改动幅度小于评审噪声，收益趋零。收益递减同样停：新稿分数低于上一稿时立即回退到最佳版本，没有这条，反思循环可能在两个版本之间来回震荡。

ReflectionLoop 还保留了每轮的问题清单：

round 0: score=0.25 issues=['篇幅不足（22 字）', '缺少来源引用标记 [n]', "缺少要点：['重规划', '上限']"]
round 1: score=1.0  issues=[]
通过=True 轮数=1

问题清单比分数更有用：它是下一轮修订的输入，也是事后归因的证据。

6.3 评审器怎么写

一个可解释的评审器只需要四类检查（HeuristicCritic）：

critic = HeuristicCritic({
    "min_chars": 120,
    "require_citation": True,
    "required_terms": ["重规划", "上限"],
    "banned_phrases": ["众所周知"],
})

四类检查分别是长度、结构、要点覆盖与空话检测。长度防敷衍，但不该作为主要指标；结构看引用标记、编号与字段是否齐全；要点覆盖看任务要求的关键概念是否出现；空话检测针对"众所周知""毋庸置疑"这类填充。

要避免的评审器是"让模型自由发挥地挑毛病"：它倾向于给出风格化建议（"可以更生动"），而这些建议无法被验证，也无法收敛。

需要模型评审时，用成对比较代替绝对打分：给两份稿子，问"哪份更好地满足了下列三条标准"。成对比较的稳定性显著高于 1—10 分制，也更容易做成 A/B 评估。

6.4 自一致性：用采样换稳定

在不改变模型的前提下，多次采样再投票是最便宜的稳定性手段：

self_consistency(["方案 A", "方案 A", "方案 B"])
# {'answer': '方案 A', 'votes': 2, 'total': 3, 'agreement': 0.667}

适用条件：任务有离散答案（分类、选项、是否），且单次采样成本可接受。对开放式写作无效，三篇不同的文章没有"多数票"。

6.5 自愈代码

代码任务有最理想的反馈源：解释器。CodeHealer 的循环是"执行 → 抓错 → 让模型改 → 再执行"：

healer = CodeHealer(fixer=fix, max_rounds=3, timeout=5.0)
result = healer.run("print('hello'\n")   # 语法错误
# {'ok': True, 'rounds': 1, 'output': 'hello'}

隔离执行靠三样东西：子进程、超时与独立临时目录。这是最低限度的隔离，生产环境应当换成容器或专用沙箱。回灌时只保留错误堆栈的末尾 20 行与异常类型，完整堆栈往往几百行，全塞回去只会挤占上下文。轮数限制在 3 轮，修复循环很容易在"改坏—再改"之间震荡。

自愈的收益随错误类型差异很大：语法错误几乎一次就好；逻辑错误（结果不对但不报错）需要测试断言，否则模型无从判断自己是否改好了。

6.6 什么时候反思无效

情形原因替代方案
信息不足评审也无法凭空补出事实先补检索或追问
标准模糊没有可判定的 rubric先写验收标准
模型能力上限它不知道自己错在哪换更强模型或拆任务
已经收敛改动小于噪声停，进入评估环节

表格末行最容易被忽略：团队常常在"再改一版"上花掉比"重新设计"更多的预算。

工程要点

评审器与生成器用不同的提示，最好用不同的模型；同一提示自评，倾向于自我确认。每轮保存完整版本，便于回退与对比，只保存最终稿会丢掉最有价值的对照。

反思的收益要计入成本：三轮反思等于三次生成加三次评审，用在简单任务上通常不划算。对结构化输出，反思应当退化为校验加重试一次，开放式改写没有意义。

常见失败模式

没有标准的反思等于没有反思：提示只写"请检查并改进"，模型只会做同义替换。分数漂移会让循环在两个版本之间震荡，同一稿两次评分差 2 分就足以触发。越改越差源于缺少回退机制，最终那一版反而可能是最差的。评审泄露更隐蔽：把参考答案放进评审提示，评审判定"通过"，但答案其实是抄的。

练习

  1. 给 HeuristicCritic 增加"引用编号必须连续"的检查，并构造一个不连续的样例。
  2. 用 ScriptedLLM 模拟一个"越改越差"的模型，验证 ReflectionLoop 会回退到最佳版本。
  3. 给 CodeHealer 增加一个"两次补丁相同则停止"的判定，解释它防的是什么。

07 · 检索增强：把记忆换成可核验的资料

RAG 的收益来自可核验：每条结论都能被指回一段原文。上下文再长，没有引用的 RAG 也只是把幻觉换了个来源。

学习目标

读完本章，应当能够说清 RAG 链路上每一段的职责与该段的典型失败，按文档类型选择切分粒度与重叠比例并解释参数变化的后果，说明 BM25 与向量召回为何互补、RRF 为什么比分数加权更稳，并用召回率、引用覆盖率、忠实度三个指标评估链路。

7.1 三种知识来源的取舍

来源时效可核验成本适用
参数记忆（模型权重）训练截止否已支付常识、语言能力
上下文注入（RAG）实时是（有原文）检索 + token政策、文档、内部知识
工具查询（API/SQL）实时是（有返回值）一次调用结构化数据、精确计算

三者的边界要提前划清。参数记忆能提供的只有训练截止之前的常识与语言能力，凡是需要指出出处的结论都不应落在权重里；上下文注入能提供实时资料，代价是检索加 token；工具查询返回精确值，适合结构化数据与计算。能用 SQL 得到精确数字的场景，不要用 RAG 去读文档找数字，后者既慢又容易错。RAG 擅长的是非结构化文本里的语义匹配，例如同一制度的不同表述或条款关联。

7.2 链路与职责

阶段职责典型失败

7.3 切分：参数与后果

chunks = chunk_text(text, size=320, overlap=60, source="policy")

块长取 200 至 400 字，是中文文档的常用区间。切得太碎，单块缺少上下文，答案容易断章取义；切得太大，检索精度下降，还会占用过多预算。重叠取 10% 至 20%，防止答案被切在边界上，代价是索引膨胀与重复召回。切分点优先落在句号与换行处，表格和代码块整体保留，并单独标注类型。一个常被忽略的事实是，切分策略决定了召回率的上限：答案一旦被切散在两个块里，再好的重排也拼不回来。评估时应当专门检查期望引用的块 id 是否被切分破坏，这一步能解释相当一部分召回失败。

7.4 混合检索与 RRF

BM25 与向量召回擅长的东西不同。BM25 依赖词频与逆文档频率，对精确词极强，型号 X200-Pro、错误码 E1024、专有名词都靠它兜住，遇到同义改写则无能为力。向量召回依赖语义空间，同义表达是它的强项，对精确字符串偏弱，容易给出看起来相关但答非所问的结果。两路各取 top-k 再融合，才能同时覆盖这两类查询。

融合两路最省心的方式是倒数排名融合（Reciprocal Rank Fusion）：

$$ \text{score}(d)=\sum_{r\in\{\text{bm25},\text{dense}\}} \frac{1}{k+\text{rank}_r(d)},\quad k=60 $$

它只用排名、不用分数，不必把两种量纲校准到一起，这也是它比分数加权更稳的原因。代价是丢掉分差信息，当第一名遥遥领先时，RRF 会把这点优势抹平。若业务对强匹配敏感，可以在 RRF 之后叠加一个小的原始分数项。

pipeline = RAGPipeline().index(docs, size=220, overlap=40)
hits = pipeline.retrieve("记忆写入为什么昂贵？", k=3)

7.5 重排：廉价的第二次机会

召回阶段追求不漏，重排阶段追求排准。词项覆盖率统计查询词在候选块中的覆盖比例，零成本、可解释，能修正明显的排序错误。交叉编码器把 (query, passage) 一起送进模型打分，效果好，代价是每个候选一次前向，成本随候选数线性增长。工程上的折中是召回 20 至 50 个候选，用交叉编码器重排到 3 至 5 个。候选太少，重排没有发挥空间；候选太多，延迟与成本不可接受。这个区间值得在自己的语料上量一次。

7.6 生成：忠实度优先

提示词里必须写死三件事：

1. 只依据给定资料回答；
2. 资料不足时明确说"资料未覆盖"，不要推测；
3. 每个结论后用 [序号] 标注来源。

即便如此，模型仍可能引用错位：结论来自第 3 段，却标了 [1]。缓解办法是要求逐句引用，并在后处理里校验编号是否落在候选范围内，citation_coverage 做的就是这件事：

{"answer": "写入是昂贵的：抽取事实要调用模型，去重要做相似度比较……[1][2]",
 "citations": [{"id": "notes#7", "score": 0.52}, ...],
 "coverage": 0.667}

忠实度（faithfulness）比答案好不好更值得优先保障。一段措辞平庸但有据可查的答案，远好过一段漂亮但编造的答案：前者可以复核，后者只能重跑一次再赌运气。

7.7 三个评估指标

指标问题计算
召回率 recall@k该找到的资料找到了吗期望块 id ∩ 命中块 id / 期望块数
引用覆盖率答案是否标注了来源被引用的命中块 / 命中块总数
忠实度答案是否只用了资料里的内容人工抽检或模型逐句核对

前两个指标可以完全规则化，适合放进 CI；忠实度成本高，按发布节奏抽样。三者要一起看：召回率高而覆盖率低，说明模型不爱引用；覆盖率高而忠实度低，说明它在引用着编；召回率本身低，则要回头查切分与索引版本。

工程要点

索引与模型版本要绑定。换 embedding 模型必须重建索引，并在元数据里记录版本，否则召回会静默漂移，而漂移在指标上只表现为答非所问，很难归因。片段去重不能省：重叠切分会产生近乎重复的句子，生成前不去重，答案就复读同一段话。

来源元数据要保留文件名、段落号与更新时间，没有元数据的引用等于没有引用。注入量也要控制，top-3 通常优于 top-8，多出来的片段会稀释注意力，最相关的那一段反而被淹没。

常见失败模式

失败表现改法
切碎表格表头与数据分离，模型把列名对错表格整体保留并转成 Markdown
只做向量型号、错误码召回不到，用户觉得"它没看懂我的问题"补 BM25 一路，用 RRF 融合
引用幻觉答案里的 [1] 指向一段无关内容校验引用编号落在候选范围内
资料相互矛盾却不标注两个版本的制度同时被召回，模型随机选一个在证据表里显式标注冲突
把摘要当原文二次摘要过的资料被当权威来源引用，错误被放大引用指向原文而不是摘要

前两类属于建库阶段的问题，重跑一次评估就能从召回率上看出来；中间两类落在生成阶段，要靠抽检轨迹；把摘要当原文要在入库时拦住，事后很难分辨。

  2. 关掉 BM25，只用向量召回，构造一条包含型号的查询，比较两种配置的命中差异。

08 · 多智能体：先证明单智能体不够用

多智能体的收益来自"角色专业化 + 独立上下文"，代价是通信开销与错误传播。绝大多数场景不需要它。

学习目标

读完本章，应当能够用三条判据判断是否真的需要多智能体，区分四种拓扑的通信成本与错误传播路径，实现一个主管式系统并说明分派与合并为什么是最容易出错的两处，并估算多智能体的真实成本，给出可接受的轮数上限。

8.1 三条判据

满足全部三条，才值得引入多智能体。角色要确实异质：不同角色需要不同的系统提示、工具集或知识边界，这些差异无法用一段提示表达。上下文要确实会互相污染：把两类工作放进同一上下文会显著降低质量，审稿需要挑剔，写稿需要发散，这两种要求放在一起会互相抵消。错误要能被隔离：一个角色的失败不会无声地污染全局，或者有明确的仲裁机制。三条里缺一条，单智能体加更好的工具与提示通常更便宜、更可控。

多智能体不会让模型变聪明，只会让不同的提示各自发挥。单角色提示没写好，拆成三个角色只会得到三份没写好的输出，还要多付几倍的调用费用。

8.2 四种拓扑

图 8-1　从左上到右下：通信成本与调试难度递增。

拓扑通信优点风险适用
流水线单向传递可调试、可插人工上游错误原样下传写作、ETL
主管星型职责清晰、易扩展主管瓶颈、合并丢信息多来源调研
辩论双向对抗压测论证、暴露盲点同质化、成本 ×N判断类任务

8.3 消息还是共享状态

两种协作机制的选择，取决于任务是否需要阶段性共识。消息传递用于主管与流水线，每个角色只看到自己被交给的任务与必要上下文，好处是上下文干净，坏处是无法感知全局进展。共享状态用于黑板，所有角色读写同一份带版本的事实，信息对称，代价是需要冲突解决与收敛判定，而这两件事本身就要写不少代码。

Blackboard 的最小实现只有写、读、历史三个操作，关键是写入幂等：值未变则不产生新版本，这样"事件数不再增长"就可以作为收敛判据。

board.write("k", 1, "a")   # version 1
board.write("k", 1, "b")   # 值未变，仍为 version 1
board.write("k", 2, "b")   # version 2

8.4 主管式系统

supervisor = Supervisor(
    workers=[researcher, writer, reviewer],
    plan=lambda task: ["梳理事实", "撰写初稿", "审校定稿"],
    assign=lambda sub: {"梳": "researcher", "撰": "writer", "审": "reviewer"}[sub[0]],
)
result = supervisor.run("写一篇关于智能体评估的短文")

分派与合并是最容易出错的两处。分派靠关键词匹配角色名，在真实任务上很快失效，稳妥做法是让主管输出结构化的 {"subtask": ..., "role": ...}，并对未知角色做兜底。合并的默认实现是把各角色的输出按标题拼接，这会丢掉冲突信息，更好的合并是先列冲突再裁决，并保留每个结论的来源角色。主管还有一个隐性成本：它是单点。一次错误分派会让三个专家白干，主管的上下文也会随子任务增多而膨胀，实践中应限制子任务数，3 至 5 个为宜。

8.5 辩论：何时有用，何时是浪费

辩论的价值在于暴露盲点，它并不负责投票选出正确答案。它适合方案取舍（A 还是 B 且两边都有道理）、需要有人专门唱反调的风险评估，以及需要交叉质证的事实核验。有客观答案的计算题直接算更快，创意生成在对抗中会收敛到平庸，成本敏感的场景每轮都是 N 次调用，这三类都不适合辩论。最大的风险是同质化：正方与反方由同一个模型扮演时，论点往往镜像对称，看似激烈，实则没有新信息。缓解办法是给双方不同的材料与不同的评分标准，条件允许时换用不同模型。

8.6 错误传播与收敛

多智能体系统的失败，常见形态是错误在角色之间往返放大，单个角色出错反而容易发现。研究员把不确定的结论写成肯定句，撰稿人照抄并加上更肯定的措辞，审校只检查语句通顺而不核对事实，最终交付一份语气坚定、事实存疑的报告。整条链路上没有一处报错，每一棒都在上一棒的基础上又加了一点确定性。

三道防线可以挡住这类放大。证据随结论走，每个结论必须带来源，没有来源的结论在合并阶段被降级；审校有否决权，不通过时回到撰稿，直接交付的口子要堵住；全局设预算，给整个协作定 token 与轮数上限，避免越讨论越贵。

8.7 成本模型

设 $N$ 个角色、$R$ 轮、每次调用平均 $T$ token，则总成本约为

$$ C \approx N \cdot R \cdot T \cdot c $$

其中 $c$ 为单价。对比单智能体的 $R \cdot T \cdot c$，多智能体的成本是 $N$ 倍。这解释了为什么多智能体在 demo 里惊艳、在生产里昂贵：它买到的是并行的专业化，推理能力本身没有变好。

一个实用的止损线：如果单智能体在评估集上的通过率已经 ≥ 85%，再上多智能体的边际收益通常不足以覆盖成本。

工程要点

角色名、职责、输出格式都要写进系统提示，且彼此不重叠。每次交接都记录 sender / recipient / 摘要，否则排障时无法还原决策链。

合并阶段必须能表达两个角色结论冲突这种情况，不能强行合成一段通顺的话。每个角色还要有独立预算，避免一个话多的角色吃掉全局额度。

常见失败模式

失败表现改法
角色重叠三个角色都在"分析"，只是措辞不同，等于同一个模型调用三次让职责与工具集互不重叠
无仲裁两个角色给出相反结论，系统直接把两段都贴进最终答复合并阶段先列冲突再裁决
无限对话角色之间互相"补充意见"，没有轮数上限设全局轮数与 token 上限
上下文串味把审校的挑剔语气带进撰稿上下文，导致越改越保守每次交接只传必要摘要，不传全量上下文

这四类问题在 demo 里都不明显，因为演示用的任务短、角色少、语气统一。任务一长，角色重叠先表现为成本上升，无仲裁表现为答复自相矛盾，无限对话与上下文串味则要等轨迹攒够才能看出来。

09 · 图编排：把循环变成可暂停的状态机

当一个 Agent 需要"停下来等人"、"失败后从中间恢复"、"跑完还能重放"，它就不再是一个函数，变成了一张状态图。

学习目标

读完本章，应当能够判断什么时候必须从手写循环升级为图编排，设计可序列化的状态并说明哪些东西不能进状态，用检查点实现中断恢复、用幂等键避免重放时重复副作用，并说清人工审批（HITL）的暂停与恢复语义。

9.1 三个升级信号

手写 while 循环能覆盖大部分单轮任务。只有出现下面三类需求中的任何一类，才值得引入图编排：需要暂停等人，例如审批、补充信息、人工接管；需要从中间恢复，例如进程重启、超时重试、跨天任务；需要分支与合并，例如不同路径汇合到同一节点，或多路并行后聚合。三类都不需要时，一个带预算的循环更简单，也更好调试。

图 9-1　节点是纯函数，边是判定；检查点让整张图可以暂停、恢复、回放。

9.2 状态设计三原则

状态必须可序列化。数据库连接、文件句柄、线程锁都不能放进去，所有外部依赖通过节点函数注入，不挂在状态上。这条约束在单机上显得多余，一旦要落盘、要跨进程恢复，它就成了硬要求。

状态要最小化。只放恢复执行所必需的东西：消息、计划、工具结果、预算计数、版本号。派生数据应当现算，例如渲染好的提示词，放进状态只会让状态与代码不一致。

版本要显式。状态带 schema_version，节点在读取时校验。没有版本号的状态，一次字段重命名就会让所有历史检查点失效。

state = {
    "schema_version": 2,
    "messages": [...],          # 对话与观察
    "plan": {...},              # 计划及其步骤状态
    "tool_results": {...},      # 已执行工具的缓存（幂等重放用）
    "budget": {"tokens": 1200, "steps": 3},
    "pending_approval": None,   # HITL 的挂起点
}

9.3 检查点与幂等重放

检查点由状态快照、版本号与时间戳组成，每一步之后写一次。恢复时从最近的检查点加载，从下一个节点继续。这里有一个隐蔽的坑：重放会重复执行副作用。若第 3 步已发出退款，恢复后又执行一次，就是重复退款。两道防护挡的是不同情况：工具结果缓存把 tool_results[call_id] 存进状态，重放时命中缓存直接返回，不再调用；幂等键对每次副作用调用生成 idempotency_key(tool, arguments)，服务端按此去重。只做第一道不够，缓存可能丢失，换机器或者状态被截断都会丢，服务端的幂等才是兜底的那一层。

9.4 人工中断的语义

HITL 是一个正式的状态，不能用一个弹窗代替。

阶段系统行为需要落盘
触发判定为高风险，写入 pending_approval待批动作、参数、理由、超时时间
暂停停止推进，释放执行资源完整状态快照
恢复批准则继续，拒绝则改道审批人、时间、决定、备注
超时按预设策略处理（默认拒绝）超时事件

设计上有三个要点。默认拒绝，没有审批人响应时系统不能默认通过；可改道，拒绝之后不一定要终止任务，可以走降级路径，转人工、只读查询或者告知用户；审批可审计，谁、何时、依据什么批准，都要能被查出来。

9.5 条件边：确定性优先

边的判定函数应当尽量由代码完成，把模型留给确实需要判断的地方。

def route_after_check(state):
    if state["check"]["ok"]:
        return "end"
    if state["check"]["needs_human"]:
        return "hitl"
    return "replan"

确定性的边可测试、可复现；让模型决定下一步去哪，会把分支数量与不可预测性同时放大。确实需要模型判断时，让它输出受限枚举（pass / hitl / replan），再由代码映射到边。

9.6 与手写循环的对比

维度手写 while图编排

中断恢复需要自己实现检查点天然支持

判据仍然是 9.1 的三条信号。为一张只有三个节点、没有分支的图引入完整编排框架，收益通常为负。

9.7 落地建议

先把状态结构定下来，再写节点。状态改一次，节点全改，这个顺序反过来会付出成倍的返工。每个节点保持纯函数，输入状态、输出状态增量，副作用集中在少数动作节点里。检查点写入要幂等，同一 step_id 重复写不应产生两条记录。整张图还要设一个最大节点数，防止条件边形成环。回放时用同一份检查点加同一份工具缓存，保证结果可复现，模型的非确定性除外，可以用固定种子或脚本模型。

工程要点

状态里只放可序列化的字段，连接、句柄、锁一律通过节点注入。检查点与工具缓存要一起落盘，只存状态不存缓存，重放时仍然会重复调用工具。

中断点要显式记在状态里：待批动作、审批人与超时策略，少一样都无法事后审计。副作用集中在少数动作节点，恢复时能复现的部分才多。

常见失败模式

失败表现改法
状态塞了不可序列化对象上线后检查点写入失败，恢复功能形同虚设状态只放可序列化字段，依赖通过节点注入
重放重复副作用没有幂等键，恢复后重复发消息、重复扣款工具结果缓存加服务端幂等键
HITL 超时默认通过把"没人管"当成"同意"，是典型的安全事故超时按默认拒绝处理
图里藏环条件边在某些输入下互相跳转，任务永不结束设最大节点数并加环检测

10 · 评估与可观测：没有度量就没有迭代

智能体的质量要看同一批用例上的通过率与成本，而不是"感觉变好了"。

学习目标

读完本章，应当能够搭起规则断言、轨迹指标、模型评审三层评估，从真实事故里长出一组回归用例，用轨迹判断失败属于模型选错还是工具不稳，并设计发布门禁，让变差在合并之前被发现。

10.1 为什么评估必须先行

传统软件里回归测试是标配，智能体项目里它常被推迟到功能稳定之后。结果是改动靠手感，退化靠用户投诉发现，同一个 bug 要修三次。评估的最小可行版本只需要一天：10 至 30 条用例、几条断言、一个脚本，先把这批用例跑通，再谈优化提示词。它带来的最大变化体现在讨论方式上，从"我觉得这个提示更好"变成"它在用例 7 和 12 上退化了"。前者无法验证，后者能立刻定位到具体输入与具体断言。分数只是副产品，讨论方式的变化才是这类项目最缺的东西。

图 10-1　用例 → 运行 → 轨迹 → 断言 → 门禁 → 归因，闭环的每一段都要自动化。

10.2 三层评估

层频率成本回答的问题
L1 规则断言每次提交毫秒该调的工具调了吗？超步了吗？
L2 轨迹指标每次提交毫秒步数、错误率、token、P95 时延是否退化
L3 模型评审按发布节奏秒/条开放性质量是否提升（rubric / 成对比较）

L1 与 L2 必须进 CI，L3 用于版本对比，不进每次提交。把 L3 塞进 CI 的直接后果是构建变慢、费用上升，评审分数抖动还会带来大量误报，团队很快就会学会忽略红色标记。

10.3 用例：从事故里长出来

一条好的用例包含五个字段：

EvalCase(
    id="refund_boundary",
    task="客户订单金额 4999 元，要求退款",
    expected_terms=["审批"],
    required_tools=["lookup_policy"],
    forbidden_tools=["issue_refund"],     # 超阈值不得直接退款
    max_steps=6,
)

expected_terms 是答案必须包含的关键词，用起来要谨慎，容易变成背答案；required_tools 与 forbidden_tools 是比文本断言更稳定的行为断言，前者保证该查的政策查了，后者保证超阈值的动作没有发生；max_steps 防止答对了却绕了十步的情况。

用例有三个来源：线上事故的价值最高，产品需求边界与模型已知弱点各占一部分。每条线上事故修复后都应补一条对应用例，否则同一个坑会再踩一次。

10.4 轨迹指标

一次运行产出的事件流可以算出下面几个指标。

指标计算退化信号
步数agent.end.steps中位数上升 30%
工具错误率失败 tool.call / 总数超过 5%
重复调用率同工具同参数出现次数 / 总调用出现即需排查
token / 任务agent.end.tokens上升 20% 而通过率不变
P95 时延各步骤耗时求和的分位数超过 SLA

这些指标的价值在于归因。通过率下降而步数不变，多半是工具或数据出了问题；步数上升而通过率不变，多半是提示或工具描述变差。两类信号指向的修复位置完全不同，混在一起看就只能靠猜。

10.5 rubric 与成对比较

开放性任务（写作、方案）无法用关键词断言，两种折中都可以落地。rubric 打分把质量拆成可判定的条目，逐项打分再加权。

rubric_score(answer, {"引用 覆盖率": 1.0, "缺少项": 1.0})
# {'score': 0.5, 'detail': [...]}

成对比较给评审两份答案，问哪份更好地满足标准 X、Y、Z。它比绝对打分稳定，天然适合 A/B：同一批用例上新旧两版各跑一次，统计胜率。两种方法都有位置偏差与长度偏好，缓解手段是交换顺序再评一次，只保留两次一致的结论。

10.6 发布门禁

门禁不需要复杂，四条足够：L1 通过率不低于基线，不允许下降；禁止工具从未被调用，forbidden_tools 零命中；token 中位数不超过基线的 120%；新增用例全部通过。门禁的意义在于把质量变成合并条件的一部分，没有门禁的评估只是每月一次的报告。

10.7 生产可观测

上线后需要的是另一组信号，重点从对不对转向稳不稳、贵不贵。按 stopped_reason 分组，max_steps 与 loop_detected 的比例是健康度的先行指标；按工具分组看错误率、P95 时延与截断率，截断率升高说明返回体在变大；按用户分组看 token 消耗的 P99，用于发现异常调用。每天再抽样人工看 10 条完整轨迹，这比任何仪表盘都有效。

------------------------------------------------------------------------------
calc                        True    1.0     557       -

------------------------------------------------------------------------------

工程要点

用例集要进版本库，与代码一起评审。断言优先于打分，能写成规则的，不要交给模型评审。

每次评估都要保存轨迹，否则失败无法复盘。评估脚本要能在本地用一条命令跑完（python -m learning_agents.demo eval），否则没人会跑。

常见失败模式

失败表现改法
只测成功路径用例全是"正常问题"，一上线就死在边界条件补边界与异常用例
断言文本不测行为模型换一种说法就判失败，误报多了团队关掉评估用工具调用与步数做行为断言
用例泄漏用例与提示词一起调，模型"背下"了用例，分数虚高用例集单独维护，不参与调参

这四类问题的共同后果是让数字失去解释力：只测成功路径会漏掉实际出事的场景，断言文本会带来误报，用例泄漏让分数虚高，没有基线则连退化都看不出来。

11 · 案例 A：深度研究助手

研究类任务的验收标准只有一条：每条结论都能回到一段原文。本章把前七章的能力装成一条可交付的流水线。

11.1 需求拆解

输入是一句开放式问题，例如"过去两年，检索增强在企业知识库场景的主要失败模式有哪些？"，输出是一份带引用的简报。五项验收标准各有一套机制支撑，缺一项就会在某个环节暴露。

要求含义对应机制
多源至少三个独立来源并行检索
可核验每条结论有编号引用证据表 + 引用核查
可追溯能回到原文段落块 id 与来源元数据
有边界资料不足时明说覆盖率阈值 + 显式声明
可复现同一输入可重跑固定检索参数 + 轨迹

图 11-1　分解 → 并行取证 → 证据表 → 写作 → 引用核查。红色回路是"缺引用就回去补检索"，最多两次。

11.2 五个阶段

五个阶段依次是问题分解、并行取证、证据表、写作与引用核查，前两个阶段产出候选材料，后三个把材料变成简报。

分解把大问题拆成 3—5 个子问题，每个子问题对应一次检索。子问题互相重复会让证据同质化，拆得过细又检索不到，整条流水线的上限在这一步定下。

plan = Planner().from_template([
    "RAG 在知识库场景的典型失败模式",
    "失败模式的成因分类",
    "业界的缓解手段与效果证据",
])

并行取证让每个子问题各走一条检索链路，网页、论文与本地库分别记录来源类型。并行压缩的是延迟，代价是结果需要去重。

hits = {q: pipeline.retrieve(q, k=4) for q in sub_questions}

证据表是最关键的结构，每条证据记下主张、原文片段、来源 id、发布时间与可信度；片段不超过 200 字，可信度取 0 到 1，由来源类型与多源一致性决定。

@dataclass
class Evidence:
    claim: str          # 一句话主张
    quote: str          # 原文片段（≤ 200 字）
    source_id: str      # 块 id，可回溯
    published: str      # 发布时间
    confidence: float   # 0-1，由来源类型与一致性决定

有了证据表，写作就变成选证据与组织语言，引用成为结构约束，不必等到成稿再补标。段落按证据组织，每段先给结论再给支撑，证据表之外的事实一律不许引入。这条规则要写进系统提示，并在核查阶段逐条验证。

引用核查逐句追问三件事：这句话有编号吗，编号落在候选范围内吗，编号对应的原文是否真的支持它。前两项可以规则化，第三项要靠模型判断或者人工抽查。

coverage = citation_coverage(draft, hits)
if coverage < 0.8:
    return re_retrieve(missing_claims)   # 最多两次

11.3 冲突处理

多源研究必然遇到相互矛盾的资料，例如两个版本的行业报告，或者两篇结论相反的论文。处理方式有三种，可靠性依次下降。并列呈现写明"来源 A 认为……，来源 B 认为……，差异可能源于样本不同"，这是最诚实的做法。按可信度加权先给来源打分，官方文档高于同行评议，同行评议高于博客，采纳高分来源并注明理由。按时间取新只适用于价格、政策这类事实随时间变化的场景，学术争论不能这样处理。最差的做法是让模型"综合一下"，生成一段看不出矛盾的平滑叙述。

12 · 案例 B：客服工单处理

高频问题走确定性路径，长尾问题才交给自主循环；不可逆动作必须审批。这是投入产出比最高的智能体形态。

12.1 为什么从工单切入

工单场景适合做智能体，理由有三条：量大，样本足够撑起统计结论；边界清晰，政策本来就可以写成规则；反馈明确，用户是否被解决可以直接观测。它同时有三个陷阱，退款、发票与投诉都涉及不可逆动作，一旦出错就是真金白银的损失。

合理的结构因此分成三层。路由器处理 80% 的常规请求，走确定性路径；自主循环只接描述含糊、多意图混合的长尾；审批门卡住所有不可逆动作。

图 12-1　三条确定性路径 + 一个升级出口。红色节点是不可逆动作的闸门。

12.2 意图与路径

意图判定依据路径工具风险
退款含"退款""退货"且订单号存在查政策 → 校验资格 → 审批lookup_policy、get_order高（资金）

路由靠一张关键词表实现，代码里的四个意图分支加上兜底，与上表一一对应：

router = Router({
    "refund": ["退款", "退货", "退钱"],
    "invoice": ["发票", "开票", "抬头"],
    "logistics": ["物流", "快递", "没收到"],
    "complaint": ["投诉", "太差", "差评"],
}, fallback="other")

关键词路由在真实语料上的准确率通常在 80%—90%，剩余部分靠兜底分支接住。兜底不应当做成"再问一遍"，那会让用户重复描述；兜底要直接给出可执行的下一步，转人工或者给自助入口。

12.3 政策校验：把规则写进代码

退款资格属于规则明确但条件多的判断，适合用一个函数写死：

def check_refund_eligibility(order: dict) -> tuple[bool, str]:
    if order["days_since_delivery"] > 7:
        return False, "超过 7 天无理由退货期"
    if order["status"] not in ("delivered", "completed"):
        return False, f"订单状态为 {order['status']}，不可退款"
    if order["amount"] > 5000:
        return True, "金额超过 5000，需人工审批"
    return True, "符合自动退款条件"

这段判断不交给模型，理由不在模型能力，而在规则本身会变、会审计、会被质疑：代码有 diff、有测试、有责任人，提示词这三样都没有。

模型的位置在规则之外：理解用户表达的诉求，把规则结果翻译成人话，判断是否需要升级。分工清楚，系统才稳。

12.4 审批门的位置

审批门要卡在动作之前，等结果出来再审批已经没有意义：

registry.hook = ApprovalGate(
    approver=ops_console.approve,
    require_for={"issue_refund", "send_compensation"},
).hook

三个细节决定这道门是否真的有用。审批人看到的应当是结构化动作，金额、订单号、政策依据都在界面上，而不是一段自然语言摘要；超时默认拒绝，并给出转人工的降级路径；审批记录进工单，事后可以追溯是谁批的。

12.5 评估用例设计

评估用例至少要覆盖四类边界：

类型例子断言
金额边界4999 元 / 5001 元后者必须停在审批门
时效边界第 7 天 / 第 8 天后者必须拒绝并解释
政策版本旧政策下的订单按订单创建时的政策判断
工具异常物流接口超时不得编造轨迹，必须说明查询失败

第三类最容易被忽略：政策更新之后，历史订单应当按创建时的政策处理，否则会出现按新规拒绝老订单的投诉。

12.6 上线节奏

上线分四步走。先跑两周影子模式，系统只生成建议、不执行动作，人工对照后统计建议采纳率；采纳率站住之后，发票与物流查询先自动，退款仍需人工点确认；采纳率稳定在 95% 以上，再把小额退款自动化，只保留大额审批。回滚开关按意图维度设置，出问题时关掉一条路径，不必整体下线。

每一步都要有对应的评估用例与告警指标。没有回滚开关的自动化，等于把事故的影响面交给运气。

12.7 常见失败

最常见的一类失败是模型直接承诺"我们会全额退款"，而系统里根本没有执行退款。承诺必须由动作产生，语言本身兑现不了。第二类是把政策写进提示，政策一改就要改提示，而且无法测试，政策应当是代码或者配置。审批门也可能形同虚设，审批人只看到一个"是否同意"按钮，没有金额与依据，只能盲批；兜底同样容易出问题，用户说不清，系统反复澄清，几轮之后用户放弃。

练习

  1. 用 Router + PlanAndExecute 实现退款路径，要求金额 > 5000 时停在审批门。
  2. 为"政策版本"构造两条用例：同一订单在旧政策下可退、新政策下不可退，验证系统按订单时间判断。
  3. 设计一个"影子模式"开关：只记录建议不执行，并统计建议与人工决策的一致率。

13.3 成本工程

智能体的成本有三个乘数：步数、上下文长度、调用次数，对应的杠杆与风险如下表。

杠杆做法风险
降步数路由替代循环、缩小 max_steps复杂任务被截断
降上下文摘要、检索替代全量、精简工具描述丢关键信息
降次数缓存、批处理、小模型分流缓存不一致

一个实用的做法是按任务分层用模型，路由与抽取交给小模型，规划与写作交给大模型。分层之后总成本通常能降 40%—70%，端到端质量下降有限，前提是每一层都有评估。

另一个常被忽略的成本项是失败重试：一次失败任务可能消耗掉三次成功任务的预算。把 stopped_reason 纳入成本报表，才能看到成本的真实分布。

13.4 反模式清单

架构上最常见的四种错误是：用多智能体去解决提示没写好，用自主循环处理本该写死的流程，把政策、权限、金额阈值写进提示词，在没有评估集的情况下比较两个方案。实现层面的错误更琐碎，也更难在评审时发现：工具里 except: pass，截断工具输出却不标注，每次请求重建全部消息把状态丢掉，状态里放不可序列化的对象。运营层面的错误通常要等事故才暴露：只监控成功率而不看 stopped_reason 分布，没有按意图的回滚开关，上线后不再更新用例集，把"用户没投诉"当成质量指标。

13.5 团队与职责

一个能持续迭代的智能体项目需要三种角色，不必是三个人。

角色关注产出

最常见的组织问题是领域专家缺位：规则由工程师猜，例外由模型编，出了事靠客诉补齐。

13.6 如何继续学习

本库覆盖的是机制层面，继续深入可以按下面的顺序读上游的 65 篇教程（完整映射见附录 B）：

  1. 先用 agent_while_loop_from_scratch、reflection_from_scratch、plan_then_execute_from_scratch 三个 notebook 对照本库第 01、06、05 章，看同一机制在不同抽象层的写法；
  2. 再用 memory-agent-tutorial、context_engineering_from_scratch 深入记忆与上下文；
  3. 然后用 langgraph-tutorial、human_in_the_loop_approval_agent、trace_based_agent_evaluation 补齐编排与评估；

13.7 结语

智能体的工程化说到底落在三件事上：把不确定性关进循环，把循环关进预算，把预算关进评估。模型会继续变强，框架会继续更替，这三件事的次序不会变。

C.4 写作与表述说明

为便于在不同平台发布与长期维护，本库在写作上遵循以下约定：

  1. 原创表述：所有章节为独立撰写，不逐句翻译任何来源；引用他人观点时给出链接。
  2. 术语统一：同一概念只用一个中文译名，首次出现时附英文，见附录 A。
  3. 可验证优先：涉及数字、阈值、公式的地方给出推导或来源；经验值明确标注为"起点"。
  4. 不含敏感内容：不涉及个人隐私、内部系统地址、凭据、真实客户数据；示例中的订单号、门店名均为构造。
  5. 厂商中立：不以任何框架或云服务作为默认前提；示例仅依赖 Python 标准库。
  6. 可复现：所有图由 diagrams/ 下的脚本生成，所有代码可离线运行，测试覆盖核心行为。

C.5 如何贡献

  1. 新增或修改实现：补单元测试，python -m unittest discover -s tests 必须全绿；
  2. 新增插图：在 diagrams/figures_*.py 中添加函数，并在 build_diagrams.py 注册；
  3. 修改文档：保持每章结构（学习目标 → 机制 → 图 → 工程要点 → 失败模式 → 练习 → 参考）；
  4. 提交前运行 python build.py，确保 book.html 与插图同步。
